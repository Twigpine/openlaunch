# Standalone security hardening

The application security fixes previously included in bridge PR #135 are separated onto `codex/security-hardening`, based on main `70e4fa2ac1dc18832982f4d7e33ae76b80c077d8`. Their source is the reviewed combined head `be857d86006ce7ded2e26fe9903a7d16f27c90fd`.

## Scope

- Prevent upstream RPC details from leaking through API errors.
- Bound request bodies, use the shared client-IP policy, and preserve upload, post, report, profile and edit quotas across rejected requests and transaction rollback.
- Reject malformed indexer text and recover canonical chain history, derived balances, fees, points and pair-payment accounting after a reorg.
- Preserve pending launch transactions and expose recovery states without prompting a duplicate submission.
- Include the associated regression suites and contract assumption/invariant tests. Deployed contract sources, dependency pins and CI workflows are unchanged.

Bridge network support, quote/history endpoints, UI and Circle/Relay recovery remain in [PR #135](https://github.com/Twigpine/openlaunch/pull/135). In particular, uncertain Circle burns and known-hash recovery checks stay with the bridge implementation. Neither PR depends on the other to compile or run.

Two shared files require a hunk-level split: the RPC route keeps main's network selection while gaining bounded input and shared IP handling here; TradePanel gains canonical sync feedback here while the bridge PR retains its bridge-to-buy controls. All other security implementation files retain the reviewed source content, including subsequent main changes already incorporated into that source.

## Additional review repairs

The later review follow-up intentionally adds fixes beyond the source-preserving split. It addresses these verified findings:

- Receipt tracking follows a same-sender, same-nonce repricing only when the recipient, calldata and value are unchanged. Boosts sync the confirmed hash; cancelled or changed calls are reported separately.
- Pending launches retain first-buy hashes and outcomes. The last ten completed or explicitly archived launch references remain in the browser session without blocking unrelated launches. An explicit archive of an uncertain attempt requires its captured sender/nonce and a strictly greater finalized account nonce on the correct chain. Age, a missing receipt and a pending nonce never establish this. Legacy records without captured identity, smart-wallet outer senders and unavailable finality remain protected and may require manual investigation.
- Canonical advisory-lock contention returns retryable pending status rather than a misleading sync failure. Table locks keep their separate timeout. Empty holder backfill stops, failed pair-monitor work releases only its owned claim, and points readiness uses the configured chains.
- Post quota checks use the database's current clock after acquiring the wallet lock; inserted posts no longer inherit a stale transaction-start timestamp. The request reader copies bounded bytes without accumulating empty chunks or retaining oversized backing buffers. Ingress documentation clarifies how the preferred client-IP header must be sanitized.
- The payment-reconciliation runbook now covers archived evidence, canonical receipt and historical-price validation, atomic aggregate repair and preserved review decisions. The locker invariant test submits a complete withdrawal action sequence and checks the precise authorization failure.

These are bounded correctness, availability and security-hardening repairs, not a claim that every review comment describes a remotely exploitable vulnerability. Recovery depends on honest, consistent RPC responses and the documented deployment procedure. Session storage is not a cross-tab wallet mutex; denied storage retains only the current page's in-memory protection.
